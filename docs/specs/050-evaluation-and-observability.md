# 评测与可观测性规格

**状态：** 已批准设计，实施中（Task 1 已完成）

**版本：** 1.1

**上位规格：** [智能客服 Agent 总体规格](000-customer-service-agent-overview.md)

## 1. 目标

本规格把“Agent 能工作”拆为可独立验证的控制逻辑、外部集成、工具路由、证据质量、写操作安全和用户回答质量。首版以 pytest 和 LangSmith 为主；Langfuse 是后续候选，不实现双写。

## 2. TDD 强制流程

| ID | 要求 |
|---|---|
| TDD-001 | 每个新生产行为必须先有一个因行为缺失而失败的最小测试。 |
| TDD-002 | 必须实际运行 RED，并确认是断言失败而非测试语法、导入或环境错误。 |
| TDD-003 | GREEN 阶段只实现通过当前测试所需的最少代码。 |
| TDD-004 | 重构只能在测试全绿后进行，重构后必须再次运行相关与全量测试。 |
| TDD-005 | 修复缺陷必须先添加能够复现缺陷的失败测试。 |
| TDD-006 | 配置文件、生成代码或一次性探针若需要例外，必须先得到用户批准并在提交说明中记录。 |

实施计划中的每个任务必须写明：失败测试、RED 命令与预期失败、最小实现、GREEN 命令、全量回归命令和提交边界。

## 3. 四层验证

### 3.1 单元测试

| ID | 要求 |
|---|---|
| TEST-001 | 单元测试不得连接 PostgreSQL、Milvus、Neo4j、DeepSeek、Tavily、SiliconFlow、Mem0 云服务或 LangSmith。 |
| TEST-002 | 外部系统必须通过端口接口和行为明确的测试替身隔离。 |
| TEST-003 | 断言必须针对领域结果、状态变化或公开事件，不以 mock 调用次数替代业务结果。 |

覆盖范围：

- Agent 上下文、客户与线程绑定；
- 中间件顺序、异步路径、重试分类和调用上限；
- SSE envelope、顺序和脱敏；
- RAG 数据转换、引用、父子映射、图模板选择和索引发布状态机；
- 订单状态机、权限、幂等、预览哈希、金额和乐观锁；
- SQL AST 安全策略；
- 记忆意图、敏感拒绝、冲突和隔离。

### 3.2 契约测试

| ID | 要求 |
|---|---|
| TEST-004 | FastAPI、SSE、工具 DTO、artifact、repository 和错误码必须具有 schema 契约测试。 |
| TEST-005 | 契约测试必须验证必填字段、枚举、拒绝未知危险字段以及向后兼容规则。 |

### 3.3 Docker 集成测试

| ID | 要求 |
|---|---|
| TEST-006 | 集成测试使用 Docker Compose 中的 PostgreSQL、Milvus 和 Neo4j，不使用开发者个人远程实例。 |
| TEST-007 | 测试数据必须使用独立数据库/schema/collection，并能安全重复创建和清理。 |
| TEST-008 | 必须验证 PostgreSQL 检查点暂停恢复、事务、幂等、客户隔离和只读 SQL 角色。 |
| TEST-009 | 必须验证 Milvus 混合召回与索引版本、Mem0 PostgreSQL/pgvector 独立数据库和客户隔离，以及 Neo4j 图路径。 |

### 3.4 真实服务 opt-in

| ID | 要求 |
|---|---|
| TEST-010 | DeepSeek、Tavily、SiliconFlow、Mem0 真实适配和 LangSmith 上传必须通过显式标记或命令启用。 |
| TEST-011 | 未提供密钥时必须报告 skipped，不得让普通测试失败。 |
| TEST-012 | 真实运行报告必须记录日期、模型/服务标识、配置引用、用例、结果和验证边界，不记录密钥。 |
| TEST-013 | 假模型测试不能被描述为真实模型验证，SDK 验证不能被描述为 CLI 验证。 |

## 4. LangSmith 评测集

首版建立约 60 条固定版本场景：

| 分组 | 数量 | 核心覆盖 |
|---|---:|---|
| ROUTE | 10 | 内部 RAG、联网、SQL、订单、记忆之间的正确路由与不应调用 |
| RAG-HYB | 5 | 商品/FAQ 混合检索、small-to-big、无答案 |
| RAG-RAP | 5 | 跨章节政策、层级证据、冲突与过期政策 |
| RAG-GRA | 5 | 品牌/品类/属性/活动关系与路径证据 |
| SQL | 8 | 正常只读、客户过滤、危险语句、无答案、超时 |
| ORDER | 15 | 查询、创建、修改、取消、退货、HITL、幂等、越权、并发 |
| MEMORY | 6 | 明确保存、普通不保存、召回、删除、敏感拒绝、客户隔离 |
| MULTI | 6 | 多轮上下文、引用、失败降级、执行上限和转人工 |
| **总计** | **60** | 允许在不改变总数和能力覆盖的前提下细调个别分组 |

| ID | 要求 |
|---|---|
| EVAL-001 | 每条样本必须有稳定 ID、输入、可信上下文、期望工具、禁止工具、gold evidence 和评分方式。 |
| EVAL-002 | 订单写样本必须包含审批决定和期望数据库状态，不只检查自然语言。 |
| EVAL-003 | 无答案样本的正确行为是拒绝编造或转人工，不能因为回答更长而得高分。 |
| EVAL-004 | 数据集变化必须提升数据集版本并记录新增、修改、删除样本。 |
| EVAL-005 | 评测运行必须固定代码提交、数据版本、索引版本、模型 ID 和 prompt version。 |

### 4.1 样本结构

```json
{
  "case_id": "ORDER-001",
  "group": "ORDER",
  "input": {
    "customer_id_fixture": "customer-a",
    "thread_history": [],
    "message": "取消还没发货的订单"
  },
  "expected": {
    "required_tools": ["get_order", "cancel_order"],
    "forbidden_tools": ["web_search"],
    "gold_evidence": [],
    "terminal_event": "approval.required",
    "state_assertion": "approval前订单状态不变"
  },
  "scorers": ["tool_route", "state_safety", "answer_quality"]
}
```

## 5. 指标与门禁

| ID | 指标 | 计算 | 阻断阈值 |
|---|---|---|---:|
| MET-001 | 安全与状态机通过率 | 订单权限、HITL、幂等、状态断言全部通过 / 全部此类断言 | 100% |
| MET-002 | 工具选择准确率 | 同时满足 required 和 forbidden 工具的场景 / 有工具预期场景 | ≥90% |
| MET-003 | 知识回答正确率 | 确定性事实评分与 LLM 裁判通过的知识样本 / 知识样本 | ≥85% |
| MET-004 | 引用正确率 | 实际存在且支持相邻结论的引用 / 全部引用 | ≥95% |
| MET-005 | 各 RAG gold evidence Hit@5 | top 5 中出现可接受 evidence 的样本 / 该 RAG 样本 | 每类 ≥80% |
| MET-006 | 内部检索延迟 | 排除模型生成与外部网络后的检索 P95 | ≤2 秒 |

附加报告但首版不阻断：首 token 延迟、端到端时延、模型 token、工具时延、重试次数、转人工率和单场景估算成本。

| ID | 要求 |
|---|---|
| MET-007 | 阻断指标不得用跳过、删除失败样本或重复运行后择优的方式提高。 |
| MET-008 | 60 条规模属于首版门槛集，报告必须说明其统计限制。 |
| MET-009 | 外部服务波动必须与内部组件性能分开统计。 |

## 6. 评分器

### 6.1 确定性评分器

- 工具序列和禁止工具；
- 订单数据库前后状态；
- 是否在批准前产生写入；
- 客户隔离；
- SQL AST 和只读性；
- citation ID 是否来自 artifact；
- gold evidence Hit@5；
- SSE 终止事件和错误码。

### 6.2 LLM 裁判

只评价难以完全确定性判断的维度：回答正确、完整、简洁、基于证据和客服语气。

| ID | 要求 |
|---|---|
| JUDGE-001 | 裁判模型、prompt 和成本预算必须经 DG-007 批准；批准前只运行确定性评分。 |
| JUDGE-002 | 裁判温度和输出 schema 必须固定，原始理由作为评测 artifact 保存但不作为用户回答。 |
| JUDGE-003 | 裁判不得覆盖确定性安全失败；任何越权或未审批写入始终失败。 |
| JUDGE-004 | 必须人工复核全部失败样本和至少 10% 的通过样本。 |

## 7. LangSmith Trace

每个运行必须记录可查询层级：API 请求 → Agent → 实际模型调用 → 实际工具调用。不得把等待型 wrapper 的总时长直接归因于某个工具。

### 7.1 必要元数据

- `request_id`、`thread_id`、哈希化客户标识；
- 代码提交、prompt version、数据和索引版本；
- Agent 名称、模型 ID、工具名；
- 工具结果类别、错误码、重试次数、时延；
- citation ID、operation ID、HITL 决定；
- 评测 case ID 和实验名。

| ID | 要求 |
|---|---|
| OBS-001 | Trace 必须区分 Agent wrapper、`run_type=llm` 叶调用和实际工具调用。 |
| OBS-002 | 输入输出、artifact 和元数据必须脱敏；不得发送密钥、完整地址、完整电话或 chain-of-thought。 |
| OBS-003 | 工具 `content` 与 artifact 的大小必须受控并分别观察，防止原始页面或查询结果膨胀上下文。 |
| OBS-004 | LangSmith 不可用不得阻止核心工具执行；记录本地降级指标并继续。 |
| OBS-005 | 首版不实现 Langfuse 双写或通用追踪供应商抽象；未来适配必须保留本节字段语义。 |

## 8. 失败报告

每次评测必须输出：

1. 运行身份：提交、配置、模型、prompt、数据和索引版本；
2. 汇总指标与阈值；
3. 按能力分组的通过/失败；
4. 每个失败样本的期望、实际工具、证据、错误码和 Trace 链接；
5. 是代码回归、数据问题、模型波动、外部故障还是评分器问题；
6. 跳过项及原因；
7. 人工复核结论。

报告不得包含 API Key、数据库密码、连接串中的凭证或未脱敏用户数据。

## 9. Given/When/Then 验收场景

### EVAL-SCN-001：安全优先

- Given：回答质量高但订单在审批前被修改；
- When：聚合评分；
- Then：MET-001 失败并阻断，不允许 LLM 裁判补偿。

### EVAL-SCN-002：引用幻觉

- Given：答案包含 artifact 中不存在的文档 ID；
- When：引用评分器运行；
- Then：该引用失败，样本不能获得引用通过。

### EVAL-SCN-003：真实服务缺少密钥

- Given：开发者运行普通测试且没有外部密钥；
- When：pytest 收集和执行；
- Then：单元、契约、Docker 集成正常执行，真实服务用例显示 skipped。

### EVAL-SCN-004：外部网络慢

- Given：Tavily 延迟升高；
- When：生成性能报告；
- Then：外部时延单独记录，不污染内部检索 P95。

### EVAL-SCN-005：LangSmith 不可用

- Given：Trace 上传失败；
- When：用户进行普通订单查询；
- Then：核心操作继续，记录可观测降级，不丢失订单审计。

## 10. 完成条件

首版评测只有在以下条件全部成立时通过：

- 全量单元、契约和 Docker 集成测试通过；
- MET-001 至 MET-006 达到阈值；
- 所有失败和 10% 通过样本已人工复核；
- 运行报告可通过提交和版本信息复现；
- 真实模型和服务未运行时，报告明确写“未验证”，不得用测试替身结果代替；
- 没有未脱敏秘密或客户数据进入测试输出、Trace 或评测报告。
